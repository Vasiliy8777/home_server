# Анализ домашнего облака

Проект — Spring Boot 3.5 / Java 21 с файловым хранилищем, JSON-кешами,
публичными ссылками и обработкой медиа через ffmpeg, ffprobe и ImageMagick.
Основная нагрузка приходится на обход диска и внешние процессы. Выводы ниже
основаны на исходниках; замеры времени, памяти и нагрузки не проводились.

## Что очищено

- Удалены классы `RangeFileResource` и `ShareContext`: ссылок на них в проекте нет,
  они не зарегистрированы как Spring-компоненты.
- Удалены 12 неиспользуемых методов: `isFullyConverted`, `rebuildPlaylist`,
  `computeFolderSignature`, `readCreatedAtMillis`, `clearFolderCache`,
  `itemCacheFile`, `rebuildStorageScanCacheAsync`, `getOrBuildScan`,
  `invalidateStorageScanCache`, `getCachedFolderPaths`, `collectFolderPaths`, `canView`.
- Удалены недостижимая ветка кеширования сканирования, неиспользуемые поля,
  зависимость `FileService` от `MetadataService` и лишние импорты.
- Удалены закомментированные реализации Java, JavaScript и HTML.
  Поясняющие комментарии сохранены.
- Сохранены обработчики HTTP, Spring-бины, lifecycle-методы, переопределения
  и методы DTO / конфигурации, вызываемые через фреймворки.

## Приоритетные изменения

### 1. Защита файлового хранилища

`FileService.resolveSafe` проверяет нормализованный путь через `startsWith`,
но не проверяет реальную цель символических ссылок / junction. Ссылка внутри
хранилища может вести за его пределы. Для существующих файлов следует проверять
`toRealPath()` относительно реального корня; для новых — реального родителя.
Нужны проверки на Windows junction, чтение, загрузку, перемещение и удаление.

В `WebConfig` весь корень также доступен через `/media/**` после аутентификации.
Этот маршрут обходит фильтрацию `HiddenPaths` в файловых сервисах и потенциально
открывает служебные файлы и кеши. Лучше раздавать файлы через единый контроллер
с проверкой пути и скрытых каталогов.

### 2. Очередь HLS и защита от повторного запуска

В `HlsConversionService.prepareHls` проверка процесса и его запуск не атомарны.
Параллельные запросы одного видео могут запустить несколько ffmpeg, пишущих в
одну папку. Нужна блокировка по ключу и ограниченная очередь конвертаций для всех
видео. В `finally` лучше удалять конкретный процесс через `remove(key, process)`,
чтобы завершение старого процесса не удалило новый.

### 3. Кеш длительности видео и таймауты процессов

Каждый `HlsConversionService.getProgress` вызывает `getDurationSeconds`, который
запускает ffprobe. При регулярном polling это повторяющаяся работа над одним
файлом. Длительность можно сохранять по ключу файла, учитывающему изменение
оригинала. Вызовам внешних процессов нужны предельное время выполнения,
корректное чтение потоков и принудительное завершение при отмене / таймауте.

### 4. Актуальность и размер кешей

`MetadataService.readFileProperties` сразу возвращает значение из memory-кеша,
не сверяя время изменения файла. Проверка mtime есть только для дискового кеша.
Изменения оригинала вне приложения могут оставлять устаревшие метаданные.
Стоит хранить вместе со значением размер и mtime и проверять их при чтении.

`RateLimitFilter.buckets`, карты заданий `FolderPrepareService` и кеши метаданных
не имеют общего ограничения размера / срока хранения. Нужны TTL, предельный
размер и удаление завершённых заданий, чтобы память не росла с историей запросов.

### 5. Единые настройки таймаутов и lifecycle пулов

В `application.yml` async timeout — 3 600 000 мс, а в
`WebConfig.AsyncConfig` явно задано 60 000 мс. Следует оставить один источник
настройки и проверить длинные скачивания с медленного клиента.

`TomcatTimeoutConfig` задаёт keep-alive 30 минут: стоит отдельно подобрать
таймаут ожидания следующего HTTP-запроса и время операций скачивания.

Пулы `TotalCacheService`, `FolderPrepareService` и MVC executor нужно оформить
как управляемые бины либо завершать при остановке приложения. Это позволит
корректно освобождать потоки и управлять очередями.

### 6. Меньше повторных обходов диска

`FileService.list` сортирует содержимое папки перед `skip/limit`, поэтому каждая
страница снова читает и сортирует всю папку. Кроме того, подсчёт дочерних элементов
для каждой отображаемой папки добавляет отдельные обращения к диску.
Для больших каталогов полезен общий индекс / manifest с инвалидированием при
файловых операциях и периодической сверкой внешних изменений.

### 7. Разделение ответственности

`FileController` и `SharePublicController` дублируют загрузки чанками,
подготовку скачиваний и обработку медиа. Перенос этих операций в общие сервисы
уменьшит риск расхождения поведения личного и публичного API. Контроллерам
следует оставить проверку доступа и преобразование HTTP-запросов / ответов.

### 8. Проверки критичных сценариев

После первоначального анализа добавлены автоматические тесты (см. `TESTING.md`).
Для дальнейшего расширения покрытия полезны тесты границ доступа к
файлам, прав публичных ссылок, конкурентной загрузки чанков и повторного запуска
HLS. Для медиа-конвертации нужны отдельные интеграционные проверки с установленными
ffmpeg / ffprobe и подходящим GPU: в HLS используется `h264_nvenc`.

## Проверка очистки

`gradlew.bat check --offline` запускает Java- и frontend-тесты.
`npm run test:browser` проверяет личный и публичный интерфейс в headless Chromium.
Полный запуск сервера, SSL и медиа-конвертации этими проверками не покрываются.
Настройки `application.yml` в рамках очистки не изменены.
