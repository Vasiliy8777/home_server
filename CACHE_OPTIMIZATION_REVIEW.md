# Анализ кешей и передачи файлов

Этот документ описывает состояние до оптимизации. Реализованные изменения и
настройки SQLite описаны в [CACHE_MIGRATION.md](CACHE_MIGRATION.md).

Проверено 14 октября 2026 года по текущему коду, конфигурации и устройствам
хранения. Приложение и существующие кеши не изменялись. Замеры пропускной
способности, профилирование JVM и сравнение с работающей БД не выполнялись;
приоритеты ниже основаны на обнаруженных операциях, а не на обещании ускорения
в определённое число раз.

## Что хранится сейчас

| Данные | Реализация |
| --- | --- |
| Карточки папок | `.folder_cache/<hash>/signature.json`, `manifest.json`, отдельный JSON на карточку в `items/` |
| Метаданные | `.metadata_cache/<путь>/properties/<имя>.json`, плюс неограниченный `ConcurrentHashMap` |
| Миниатюры | JPEG в `.thumbnails`, имена на основе хеша пути; существующие миниатюры индексируются при старте |
| Просмотр и видео | Файлы в `.previews`, включая HLS |
| Поиск по содержимому | JSON с описанием и вектором плюс JPEG на фото; векторы загружаются в память |
| Прогресс кеширования | Перезаписываемый JSON-журнал |
| Загрузка на сервер | Временный файл плюс JSON со списком принятых чанков |

По `application.yml` эти пути по умолчанию находятся на `G:`. Проверка устройств
показала: `G:` — SATA HDD WDC WD60EZAZ-00SF3B0, `C:` — NVMe SSD HP FX900 Pro.
Если приложение запускается с переменными среды или дополнительным профилем,
фактические каталоги могут отличаться от этих значений по умолчанию.
В проверенной папке RAW в реальном манифесте кеша 278 карточек.

## Обнаруженные затраты

### Открытие папок

`FolderPrepareService.process()` сначала строит сигнатуру всей папки: перечисляет
детей, запрашивает атрибуты и сортирует список имён. Затем `readFolderItemsCache()`
открывает JSON каждой карточки и собирает весь список. Сортировка/фильтрация тоже
выполняются над всем списком. Только после этого задача становится `ready`.

При промахе кеша сервис вызывает `FileService.list()` блоками по 200 элементов.
Каждый вызов заново перечисляет и сортирует ВСЮ папку перед `skip/limit`.
Например, папка из ровно 10 000 элементов потребует 50 непустых вызовов плюс
последний пустой вызов: примерно 510 000 посещений элементов только на этом
этапе, вместо 10 000 при одном перечислении. Это расчёт по циклу в коде,
не измерение времени. Проверка сигнатуры, подсчёт элементов и операции с
метаданными создают дополнительные обращения к диску.

Фронтенд ждёт полного `ready` и запрашивает страницы по 1000 карточек.
`prepared-items` возвращает `subList` уже подготовленного списка: пагинация
есть в HTTP-ответе, но не ограничивает объём подготовки на сервере.

После каждого завершённого upload весь кеш родительской папки удаляется;
фоновое обновление дополнительно инвалидирует его ещё раз. Несколько файлов
в одной папке могут породить несколько полных пересборок. Нужны объединение
обновлений по папке и обновление изменившихся записей.

### Память, свежесть и конкуренция

- `FolderPrepareService.jobs` не удаляет завершённые задачи; каждая удерживает
  список карточек. Повторные открытия и сортировки накапливают копии списков.
- Кеши метаданных и статистики в памяти не ограничены размером/временем.
  Возврат из `filePropertiesCache` не проверяет изменение файла; дисковая
  проверка даты при таком попадании вообще не выполняется.
- Для открытия папки создаётся отдельный поток, а при пересборке — собственный
  `ForkJoinPool(4)`. Нужны общие ограниченные очереди и объединение одинаковых
  запросов, особенно во время массовых загрузок.
- `MetadataService.readFolderStats()` использует рекурсивный `Files.walk()`
  и собирает его в список. В этом обходе нет фильтра `HiddenPaths`: туда могут
  попадать служебные кеши и исключённые папки. Это расход ресурсов и нарушение
  общего правила исключения; заменить обходом с `SKIP_SUBTREE`.
- Обычные миниатюры именуются по пути без версии исходного файла. Для замены
  файла по тому же пути нужна проверка размера/даты или ключ версии, иначе
  возможна устаревшая миниатюра. HLS использует отдельный сервис ключей;
  эту проблему нельзя автоматически приписывать всем видеокешам.
- Фоновое кеширование создаёт много задач/Future и списки всех найденных путей.
  Прогресс миниатюр перезаписывает журнал под общим lock после каждого файла.
  Лучше ограниченная очередь и запись прогресса раз в 1–2 секунды плюс при
  остановке/завершении.

### Поиск ИИ

Сейчас запрос сравнивается со всеми векторами, затем для подходящих записей
проверяется существование/актуальность оригиналов. JSON-векторы занимают больше
места, чем массив `float32`, а старт требует чтения отдельных JSON.
Для 768 измерений бинарный вектор занимает 3072 байта без накладных расходов;
100 000 векторов — около 293 МиБ только числовых данных, сверх описаний,
объектов Java и индекса. Миграция в SQLite сама по себе не создаёт быстрый
индекс ближайших соседей: такой поиск нужно проектировать отдельно.

### Загрузка файлов на сервер

В `app.js` чанк равен 1 МиБ; чанки одного файла отправляются последовательно.
Параллелизм 3 относится к файлам, а не к чанкам одного файла. На каждую часть
сервер читает JSON-сессию, открывает `RandomAccessFile`, копирует тело через
`MultipartFile.getBytes()`, сортирует список принятых частей и записывает JSON
сессии целиком. Чем больше файл, тем длиннее этот список.

Начальные кандидаты для тестирования: чанки 4–8 МиБ, передача потоками с
ограниченным буфером, компактный bitmap принятых чанков и разумное ограничение
суммарного параллелизма. Более крупный чанк не всегда лучше на нестабильной сети.
Размер нужно брать из upload-сессии, чтобы ранее начатые загрузки с 1 МиБ
продолжали корректно возобновляться.

Прежде чем распараллеливать чанки одного файла, нужно исправить согласованность:
`readMeta(uploadId)` сейчас находится до `synchronized(lock)`, поэтому два
запроса могут перезаписать состояния, прочитанные до блокировки. Создание
временного файла также нужно согласовать с блокировкой. Необходимо проверять
ожидаемую длину каждого чанка и итоговый размер файла.

`upload-temp-dir` желательно оставлять на том же томе, что и целевые оригиналы:
тогда финальное перемещение обычно не требует копировать большой файл между
дисками. Перенос временных upload-файлов на SSD потребует учитывать стоимость
финальной передачи на HDD; это не равно переносу небольшого каталога БД.

### Скачивание и просмотр

Большие файлы и видео уже передаются браузеру напрямую, а сервер возвращает
`FileSystemResource`. Это разумная основа, и перенос метаданных в БД сам по себе
не увеличит скорость передачи байтов по сети.

Файлы до 50 МиБ скачиваются через fetch и целиком собираются в Blob: сохранение
начинается после получения всего файла, расходуется память браузера. При
приоритете быстрого начала сохранения можно передавать их браузеру напрямую,
продумав изменение прогресса/паузы в интерфейсе.

Не нужно заранее считать, что download не поддерживает Range: в Spring
обработка `Resource` может выполнять преобразование диапазонов. Возобновление
следует проверить реальными HTTP-запросами вместе с валидаторами ETag/Last-Modified.

Для миниатюр уже установлен семидневный HTTP-кеш; сначала обеспечить версию
исходного файла в URL/ключе. Полноразмерные фото для просмотра стоит дополнить
отдельным экранным превью и загрузкой оригинала по запросу. Сжатие JSON может
помочь ответам карточек, а JPEG/HEIC/MP4 повторно сжимать HTTP gzip бессмысленно.

## Предлагаемая архитектура

Для одного экземпляра домашнего сервера рекомендую SQLite на локальном SSD:

- `files`: стабильный id, родительская папка, относительный путь, имя/ключ
  сортировки, тип, размер, время изменения, состояние удаления;
- `file_metadata`: дата съёмки, размеры изображения, длительность, устройство,
  расширенный JSON метаданных;
- `derived_assets`: тип/размер миниатюры, путь к файлу, версия оригинала и
  конвертера, состояние и последняя ошибка;
- `photo_descriptions`: описание, версия модели, вектор как бинарный `float32`;
- `index_jobs` и `upload_sessions`: прогресс, ошибки, принятые части.

Индексы на родителе и полях сортировки/даты позволяют выбирать одну страницу
без чтения всех карточек. Для больших списков использовать курсор на основе
значения сортировки и id; глубокий `OFFSET` тоже имеет стоимость.
Расширяемые метаданные можно оставить JSON внутри строки БД: важнее устранить
отдельные файлы и полные пересборки, чем заменить сам синтаксис JSON.

Оригиналы, JPEG-превью и HLS хранить в файловой системе. БД содержит их пути
и версии. У файлов должны быть стабильные id, чтобы переименование не требовало
заново выполнять дорогой анализ ИИ.

Для SQLite: WAL, короткие транзакции, один контролируемый поток записи,
пакетные обновления. WAL допускает одновременное чтение и запись, но писатель
в каждый момент один; файл БД должен быть на локальном диске, не SMB/NAS.
Для загрузок сохранить согласованность подтверждений и долговечность данных,
а не отключать синхронизацию ради красивых цифр.
[Документация SQLite WAL](https://sqlite.org/wal.html).

Кеш в памяти — ограниченный по размеру/весу, со сроком жизни и явной инвалидацией.
Например, Caffeine поддерживает ограничение размера и вытеснение:
[документация](https://github.com/ben-manes/caffeine/wiki/Eviction).

Внешние изменения на диске отслеживать через WatchService с обработкой потери
событий и периодическим сверочным обходом. Внутренние upload/delete/move/rename
обновляют каталог сразу. Пока обновляется папка, можно показывать предыдущую
версию её карточек, проверяя актуальность при открытии/скачивании файла.

PostgreSQL с pgvector уместен при нескольких серверах, высокой конкуренции
записей или необходимости специализированного индекса поиска по векторам.
Для текущего домашнего сервера это дополнительные эксплуатационные расходы;
переход нужно обосновать замерами поиска и масштабом коллекции.
[pgvector](https://github.com/pgvector/pgvector).

## Порядок внедрения

1. **Без миграции:** один обход папки при промахе; ограничение задач/кешей в
   памяти; объединение обновлений; `HiddenPaths` в статистике; актуальность
   метаданных/миниатюр; запись прогресса с ограниченной частотой.
2. **Ранний показ галереи:** первые 60–100 карточек доступны сразу; метаданные
   и миниатюры дополняются по мере готовности. Для сортировки по дате/фильтров
   использовать уже сохранённый каталог или явно обозначать неполную выдачу.
3. **SQLite на SSD:** импорт существующих JSON и ссылок на готовые изображения,
   без обязательного повторного анализа фото. Импортируемые записи валидировать
   по пути, версии исходника и модели. Сохранить старые кеши до проверки миграции,
   переключить новый backend по настройке с возможностью возврата.
4. **Передача файлов:** согласованное состояние upload-сессий, потоковая запись,
   подбор чанка/параллелизма по тестам, инкрементальное обновление каталога.
5. **Поиск/медиа:** бинарные векторы, измерение времени поиска, при необходимости
   индекс ближайших соседей; версии и размеры превью; общие приоритеты фоновых
   задач, чтобы ИИ/ffmpeg/полный обход не мешали интерактивным запросам.

Промежуточная альтернатива БД — один атомарно заменяемый JSON на папку вместо
JSON на карточку. Это уменьшит число открытий файлов, но сохранит чтение всего
списка и его сортировку. CBOR/MessagePack могут уменьшить размер/стоимость
разбора, но не решат повторные обходы, инвалидацию и отсутствие настоящей
серверной пагинации. Их выигрыш здесь надо сравнивать после устранения алгоритмов.

## Что измерять до и после

- Время до первой страницы и первых видимых миниатюр: холодный и прогретый кеш,
  папки разного размера, включённая/выключенная фоновая индексация.
- Количество открытий JSON, операций перечисления и обращений к атрибутам,
  очередь/занятость HDD, RSS/heap JVM после повторных открытий.
- Скорость upload/download одного файла и нескольких: локальная сеть отдельно
  от интернета; размер чанка, задержка запросов, итоговая сборка/перемещение.
- Возобновление загрузки после перезапуска, корректность переименований и
  замены оригиналов, отсутствие повторного ИИ-анализа при импорте.
- Поиск при росте числа векторов: задержка преобразования запроса отдельно от
  сравнения векторов и проверки оригиналов.

Это даст основания назвать конкретный эффект ускорения. Смена JSON на БД
без изменения пути открытия папки и обновления кеша не устраняет главные затраты.
